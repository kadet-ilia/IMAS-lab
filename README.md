# IMAS_LaB_test — браузерный исследовательский стенд ИМАС

> **IMAS_LaB_test v0.15.0-rc.15.** Единый браузерный исследовательский стенд для шести экспериментов по киберустойчивости интеллектуальных мультиагентных систем. Все шесть экспериментов используют общую архитектуру интерфейса, воспроизводимые вычислительные ядра и научно-техническую справку. Историческая Python-модель `experiment.py` не считается побитово или математически эквивалентной современной JavaScript-реализации E1.

Программный комплекс предназначен для воспроизводимого исследования доверительно-робастного коллективного принятия решений в интеллектуальной мультиагентной системе при наличии византийских агентов, Sybil-идентичностей и ограничений коммуникационной сети.

## Ветка исправлений 0.15.0-rc.15 (06.11.2026)

**Единый стенд E1–E6.** Расчёт доверия, Автоматические решения, Коллективное решение, Опасные состояния, Каскадные последствия и Нарушение коллективного решения являются шестью равноправными экспериментами комплекса IMAS-lab. Верхнее меню, боковые параметры, результаты и справка используют общие компоненты. В справке есть кнопка возврата к последнему выбранному эксперименту и отдельное объяснение каждого исследования для неспециалистов.

**Интерфейс E2–E6.** Пошаговая топология отображается полноширинным блоком; основная диаграмма и матрица по сценариям/методам расположены рядом в равных колонках (для формального E4 диаграмма маркировок и матрица состояний). Сводная таблица всех результатов перенесена непосредственно перед паспортами ключевых показателей, без дублирования сравнительной матрицы ниже графика.

**E1: многофакторный план.** Для нулевых главных эффектов Recharts теперь показывает минимальный видимый столбец, численные оценки при этом неизменны. Добавлено сообщение о полноте шести главных эффектов и корректное переключение измеряемого показателя. Реальный Chromium CI вычисляет факторный план из 32 точек по два повторения на точку и проверяет диаграмму, таблицу шести доверительных интервалов и JSON с оценками.

**Статистическое планирование Монте-Карло.** Для пяти стохастических экспериментов E1, E2, E3, E5 и E6 добавлен общий предварительный расчёт R: заданная полуширина интервала Уилсона и плановый минимальный парный эффект с предполагаемой долей несовпадений. Пользователь отдельно подтверждает применение рассчитанного R. Формальный эксперимент E4 сохраняет единственный полный поиск достижимости; добавление к нему MC не планируется без новой вероятностной модели. E6 дополнен интервальными оценками риска по стоимости каждого отдельного прогона и парными сравнениями риска с корректировкой Холма. Это внутренние оценки **стохастической вариации модели**, не внешняя калибровка угроз или реальных ущербов.

**Остающиеся требования научной приёмки:** независимые эмпирические данные и внешние экспертные заключения отсутствуют, поэтому UP-36 остаётся открытым; редкие события и потоковые полные архивы для больших R требуют отдельной дальнейшей реализации. Все изменения только в ветке `remediation/imas-lab-scientific-integrity`, PR №3 не объединён.

## Ветка исправлений 0.14.0-rc.14 (06.11.2026)

**Надёжность архивов исследований.** Для E2–E6 введён формат `RESEARCH_STORAGE_SCHEMA=2`. Промежуточные контрольные точки и завершённые результаты в IndexedDB имеют конверт SHA-256, связывающий ключ модели/параметров с содержимым. В тестах моделируются порча данных, повторное вычисление хеша над изменёнными сведениями и отказ записи контрольной точки при превышении квоты IndexedDB. Данные прежнего хранилища версии 1 не используются в новой схеме.

**Научная приёмка UP-36.** Добавлен скрипт `scientific_release_gate.py` и отдельные unit-тесты. Скрипт формирует машиночитаемый отчёт `acceptance-readiness.json` с отсутствующими либо некорректными доказательствами: первичные **55** замечаний и их рассмотрение, внешние измерения E1/E2/E3/E5/E6, формальная независимая проверка E4, испытания на реальном оборудовании, повторный расчёт всех шести публикационных результатов и два независимых экспертных заключения. Путь и SHA-256 внешних файлов должны быть явно указаны. Проверяется, что отчёт калибровки относится к представленным исходным данным. **Независимая подлинность авторов и измерений не устанавливается только по содержимому файлов.**

CI публикует артефакт `imas-up36-acceptance-readiness`, но **не присваивает научную аккредитацию** при успешной сборке: `scientificAcceptance=false` неизменно до самостоятельного внешнего заключения. При отсутствии настоящего реестра, экспериментальных данных и подписей отчёт остаётся `blocked_missing_independent_evidence`. Пример незаполненного манифеста и протокол: [UP36_EVIDENCE_READINESS.md](audit/remediation/05_validation/UP36_EVIDENCE_READINESS.md). Исходная ветка `IMAS_LaB_test` не изменялась, PR № 3 не объединён.

## Ветка исправлений 0.13.0-rc.13 (06.11.2026)

### Полный исходный архив E3 и E5

Для графовых исследований E3 и E5 реализован необязательный режим `record_source_runs=1`. Архив сохраняет **каждый** исходный граф, очаг компрометации, таблицу случайных значений по всем дугам на всех тактах и варианты защиты каждого прогона. Сохранение осуществляется вместе с контрольными точками исследований; после остановки и возобновления исходный архив и результирующие таблицы совпадают с непрерывным запуском. Ограничения `source_run_limit` и `source_event_limit` (по умолчанию 100 и 250000 соответственно) действуют по принципу **fail-closed**: усечённый архив не объявляется полным. Тесты проверяют полноту всех сценариев, точную повторяемость, независимый пересчёт инфекций, ущерба и парных эффектов, выявляют повреждения архива.

### Журнал ограниченного формального поиска E4

Режим `record_marking_log=1` сохраняет каждую **обработанную** маркировку (маска компрометации, маска изоляции, модельный такт), все порождённые переходы и признаки фактического добавления в очередь BFS. В экспорт включены финальный фронт, вердикт, контрпример, исходные рёбра и статистика исследования. Лимит `marking_log_limit` предотвращает выдачу частичного протокола. Журнал и сам BFS проверяются отдельной независимой Python-реализацией, которая восстанавливает порядок обхода, переходы, состояние очереди, временные счётчики и границу поиска. **Полнота журнала относится к реально выполненному ограниченному поиску:** при `inconclusive` математическое доказательство недостижимости отсутствует.

### Статистический аудит и научная калибровка

`gui/src/researchStatisticalAudit.js` проверяет порядок и результаты поправки Холма на уровне семьи гипотез E3/E5; выдаёт предупреждения о малом R, редких событиях, хвостовом ES95 и недоказанной обменности знаков парных разностей. Предусмотрены отдельные **проспективные** расчёты объёма выборки для заданного минимального парного эффекта, допускаемой дискордантности и требуемой точности Уилсона; это не показатель «наблюдаемой мощности». В CI включены моделирование эмпирического покрытия 95%-х интервалов и контроль частоты ложных семейных открытий при множественных сравнениях.

`validate_external_calibration.py` — самостоятельный инструмент проверки **предоставленной извне** вероятностной выборки. Он проверяет метаданные происхождения и дубликаты, считает Brier, LogLoss, ECE и интервалы Уилсона, фиксирует SHA-256. Без реальных внешних измерений отчёт об эмпирической калибровке не существует. Даже после запуска скрипта происхождение данных и внешняя научная экспертиза остаются **не подтверждены** автоматически.

Полная программа и методика: [audit/remediation/05_validation/PROTOCOL.md](audit/remediation/05_validation/PROTOCOL.md). До появления независимых наблюдений, первичных текстов отсутствующих замечаний и актов экспертов UP-36 **не может считаться закрытым**. Штатные модульные и браузерные тесты подтверждают вычислительную согласованность, а не эксплуатационную применимость к конкретному объекту.

### UP-34 — независимая проверка полного E1 с сетью

В журнале одного детального прогона E1 (`source_event_log.schemaVersion=2`) дополнительно сохраняется начальная **экзогенная топология**: список рёбер, группы разделения, статусы византийских и Sybil-идентичностей. `test_up34_network_trace.py` на Python независимо реконструирует из этого журнала все такты сетевого моделирования, не используя вычисленные JS показатели в качестве эталона: компоненты связности, активность, отправку/потерю/доставку/просрочку сообщений, баланс очередей, доступность наблюдений, Beta, EigenTrust, три способа согласования, изоляцию и итоговые показатели. Контроль охватывает **5 различных сценариев × 19 тактов = 95 тактов**; дополнительно проведены три отрицательных теста с подменой наблюдения, времени завершения передачи и ребра графа. В сочетании с ранее выполненными 3×17 автономными тактами независимая сквозная реконструкция E1 покрывает **146 тактов**.

**Ограничение:** начальная топология и фактически реализованные случайные события берутся из JS-журнала как экзогенные данные. Этот тест не доказывает правильность распределения случайных графов или эквивалентность генераторов Python и JavaScript. Подробнее: `audit/remediation/03_parity/PARITY.md`.

### НЗ-15 — полный архив первичных данных E2 и E6

В расширенных настройках E2 и E6 появился переключатель `record_source_runs` (по умолчанию 0) и лимит `source_run_limit`. При включении сохраняются **все** прогоны каждого из четырёх сценариев, включая:
- **E2:** поагентные записи о наличии/отсутствии сообщения, полученное значение, наблюдаемый возраст, скрытые метки атаки/устаревания (только в архиве), эталонный знак, результаты трёх методов и диагностическую oracle-оценку.
- **E6:** исходно компрометированные вершины, полные таблицы случайных событий трёх шагов распространения, множество затронутых агентов, наблюдаемые значения всех агентов, эталонный знак, решения методов и оценки при фиксированных уровнях усечения 0–3.

Архив `sourceRunJournal` включается в полный JSON и может быть отдельно скачан кнопкой «Скачать исходные прогоны». Запись контрольных точек E2/E6 включает накопленный архив, поэтому после возобновления порядок и содержание всех реализаций совпадают с непрерывным запуском. Встроенный контроль `auditResultMetrics` сопоставляет число и идентификаторы прогонов с агрегированными долями правильных решений, ошибок, отказов и, для E6, средней величиной отклонения.

**Ограничение ресурсов:** архив запрашивается целиком; если `R > source_run_limit` или `4 × N × R > 50000`, запуск блокируется до расчёта. Параметр `source_run_limit` допускает значения 1–1000; по умолчанию 100. Архив E2/E6 **не** заменяет ещё не сформированный полный аналогичный архив E3/E5 или журнал всего пространства состояний E4. Скрытые эталонные метки из архива **не** используются практическими оценщиками решений. Штатные unit-тесты и настоящий браузерный сценарий Chromium проверяют выгрузку 40 реализаций E2 и E6.

**Дополнительная независимая проверка:** скрипт `test_up34_research_raw.py` заново рассчитывает **68 отдельных реализаций E2** и **76 отдельных реализаций E6** по сохранённым исходным значениям, сетевым событиям и меткам. Проверяются оценки всех алгоритмов, качество, доли отказов, риски и информационный охват. Эталонные алгоритмы реализованы на Python отдельно от испытуемого JavaScript. Полная межъязыковая эквивалентность исторического `experiment.py` и исправленного ядра не декларируется.

**Научный статус:** UP-34 частично выполнен; НЗ-15 частично выполнен; UP-36 остаётся открыт. Успешный CI не является научной аттестацией.

## Ветка исправлений 0.11.0-rc.11 (06.11.2026)

**Научный статус:** экспериментальная редакция на отдельной ветке; PR № 3 остаётся draft. Версии моделей: `trust-js-2.9.0-remediation`, `research-2027-2.9.0-remediation`. Изменения вычислительной семантики и структуры экспортов требуют повторного воспроизведения публикационных результатов.

**НЗ-07 — сквозной количественный учёт сообщений E1.** На каждом такте формируется `message_ledger` с независимыми накопительными счетчиками `proposal`, `evidence`, `total`. Проверяется равенство `attempted = delivered + lost + bandwidth_dropped + expired + pending` отдельно для каждого канала. Любое нарушение останавливает расчёт, а не маскируется визуализацией. В интерфейсе доступен экспорт `communication_ledger.json`.

**НЗ-15 — исходные события E1.** В настройках трассировки есть необязательный режим `record_source_events`, параметр `source_event_limit` (по умолчанию 50000 событий). Сохраняются исходные предложения, наблюдения, адреса и исходы передач, включая потери, ожидание и просрочку. Контроль сверяет статистику журнала и поканальный баланс. При превышении лимита происходит явная ошибка без выдачи неполной трассы как полной. `source_events.json` охватывает **одну** трассировку E1; архив исходных данных остальных исследований пока не сформирован.

**НЗ-14 — прерывание и возобновление E2–E6.** Сценарии E2/E3/E5/E6 исполняются в отдельных подтверждаемых стадиях с сохранением состояния ГПСЧ и промежуточных таблиц в IndexedDB. Для E4 сохраняются фронт BFS, посещённые маркировки, индекс и послойные счётчики каждые 8192 обработанных состояния; короткий формальный поиск заканчивается одним блоком. Переход к следующей стадии разрешён только после подтверждения транзакции записи. Хранилище защищено межвкладочной блокировкой Web Locks, версия и конфигурация проверяются при возобновлении. Отмена в середине незавершённой стадии допускает её повторное выполнение: опубликованный результат при этом не формируется из неполных данных. При возобновлении результаты проверяются на точное совпадение с непрерывным прогоном (кроме фактического времени исполнения).

**Проверки:** Node unit-тесты включают инварианты трафика, события, повреждение журнала, лимиты, воспроизводимость E2–E6, stop/resume и кэш. Chromium CI проверяет реальные Web Workers, экспорт результатов и восстановление E2 из IndexedDB после навигации и перезагрузки страницы. Для признания научной достоверности необходимы независимые математические и статистические эталоны, натурная калибровка, длительные стресс-тесты и выполнение UP-34/UP-36. Не следует считать успешный CI достаточным доказательством корректности научной модели.

### UP-34: независимая межъязыковая численная проверка

В обязательную CI включена отдельная Python-референсная реализация (не исторический `experiment.py`) и мост `gui/src/up34Bridge.mjs`. На **174 наборах общих исходных данных** сверяются Beta, EigenTrust, робастное усечение, веса E2/E6, вероятностное распространение E3/E5, ES95 и 12-тактовая сетевая доставка с очередью. Для **3 реальных прогонов E1 по 17 тактов** независимый Python-код заново воспроизводит по исходному журналу репутации, решения, изоляцию, восстановление и основные показатели. Дополнительно автоматизировано подтверждение **трёх принципиальных несовместимостей** исторической Python-модели и исправленной JS (кольцевой остов, свидетельства неактивных, fallback при отказе).

Подробная методика, проверяемые инварианты и ограничения: [audit/remediation/03_parity/PARITY.md](audit/remediation/03_parity/PARITY.md). Полная эквивалентность исторического Python-движка и исправленного JavaScript **не достигнута** и не декларируется: их модели и генераторы отличаются. Проверены строго обозначенные фрагменты общей спецификации; UP-34 остаётся частично открытым.

## Статистические области по прогонам

Для каждого шага сохраняются робастные решения независимых прогонов. По совокупности из `R` траекторий рассчитываются:

- среднее и выборочное стандартное отклонение с делителем `R−1`;
- области `mean ± 1s` и `mean ± 2s`;
- медиана и квантили `P5`, `P25`, `P75`, `P95`;
- эмпирические области `P25–P75` и `P5–P95`;
- область допустимого отклонения `x*(t) ± δ`.

Квантильные области не предполагают нормальности распределения и предпочтительны при асимметрии, мультимодальности и переключении режимов изоляции.

## Статистическое сравнение методов

Для RMSE, MAE, вероятности правильного решения и ошибки консенсуса выполняется парный percentile-bootstrap. Общие индексы прогонов сохраняют парность сравниваемых методов. В интерфейсе отображаются:

- средний эффект робастного метода относительно базового;
- 95%-й bootstrap-интервал;
- вероятность положительного эффекта;
- формализованный вывод о наличии или отсутствии подтвержденного преимущества.

Для метрик формируются гистограммы и диаграммы размаха со значениями `min`, `P5`, `P25`, медиана, `P75`, `P95`, `max`.

## Анализ чувствительности

Поддерживаются два режима:

1. Однофакторный анализ изменения доли византийских агентов.
2. Двухуровневый многофакторный план для параметров атаки, доверия, изоляции, шума и сети.

Для многофакторного плана рассчитываются главные эффекты, парные взаимодействия и таблица экспериментальных точек. Число точек и прогонов на точку задается пользователем.

## Сетевая модель и Sybil-атака

При включении сетевого режима предложения и свидетельства доступны только в пределах связных компонент. Модель учитывает:

- выбранную топологию и вероятность формирования ребра;
- случайные потери сообщений;
- целочисленные задержки доставки;
- максимальную допустимую давность последнего полученного значения;
- общий лимит доставляемых сообщений за шаг;
- временное разделение сети на сегменты;
- дополнительные идентичности, согласованно управляемые нарушителем.

На графике сетевой диагностики отображаются размер крупнейшей компоненты, число доступных предложений и доля доставки сообщений.

## Математическая и воспроизводимая интерпретация JS-переноса

Существующая Python-модель реализует рекуррентную Beta-оценку доверия, регуляризованную репутацию EigenTrust, медиану внутри компонент связности, доверительно-взвешенную робастную агрегацию после ограничения выбросов, сеть передачи предложений и наблюдений, а также временную изоляцию. В `trustEngine.js` эти же семейства математических операций переписаны непосредственно на JavaScript.

**Важное отличие:** Python использует `numpy.random.SeedSequence + PCG64`, тогда как браузерная версия — детерминированный `xorshift32` и преобразование Бокса–Мюллера. Равенство начальных числовых зёрен не даёт одинаковой случайной выборки; требовать точного побитового совпадения траекторий некорректно. Необходимо отдельно сопоставлять распределения и статистические оценки с заданными допусками, проверять влияние изменений порядка генерации случайных величин и измерять производительность. Результаты, приведённые в опубликованной статье для Python-эксперимента, не следует автоматически приписывать данному JS-переносу.

**Ограничение параллелизма:** независимые прогоны распределяются между не более чем четырьмя браузерными Web Workers. Настройка числа процессов из исходного интерфейса интерпретируется как желаемое количество потоков, а значение 0 выбирает число автоматически по доступным аппаратным ядрам. Сетевые операции и отдельные задания одного прогона не распараллеливаются. Отмена завершает Worker, поэтому после остановки восстанавливаются сохранённые контрольные точки, но результаты нескольких последних ещё не подтверждённых прогонов могут потребовать повторного вычисления. Проверка независимой статистической эквивалентности находится в стадии подготовки.

## Методические ограничения

Комплекс воспроизводит синтетический модельный эксперимент. Он не подтверждает эксплуатационную эффективность ИМАС на конкретном объекте информационной инфраструктуры. Сетевая модель является дискретной и агрегированной: она не воспроизводит конкретные протоколы маршрутизации, пакетные очереди каждого канала и криптографические затраты. Для прикладной верификации требуется калибровка на цифровом двойнике или стенде, определение предметного безопасного множества решений и измерение задержек, сетевого трафика, загрузки CPU и памяти на целевой платформе.

**Единый селектор:** «Расчет доверия», «Автоматические решения», «Коллективное решение», «Опасные состояния», «Каскадные последствия», «Нарушение коллективного решения». Название выполняемого исследования приводится в верхней части его рабочей области.

Каждый эксперимент включает граф направленных взаимодействий с подписями вершин и стрелками на рёбрах. Воспроизведение предусматривает паузу, переход вперёд/назад на один такт, возврат в начало, ползунок текущего такта и регулируемую скорость. Окраска вершин отражает моделируемые состояния (нормальное, скомпрометированное, получающее недостоверные данные, изолированное или функционально нарушенное); активные переходы дополнительно выделены. Выбор вершины раскрывает её текущий статус. Легенда и численность классов обновляются при смене такта.

После вычисления результатов используются несколько независимых форм визуального анализа:

- групповые столбчатые диаграммы сопоставляют методы и сценарии по выбранной метрике;
- линейные графики отражают изменение отдельной трассы, а для сети Петри — число исследованных маркировок;
- матрицы «агент × такт» позволяют проследить развитие нарушений;
- численные матрицы «сценарий × метод» кодируют величину выбранного показателя оттенком;
- сводная таблица перечисляет все рассчитываемые показатели и параметры сравнения.

В эксперименте E1 «Расчет доверия» используются графики решений и репутации, тепловая карта состояний, Монте-Карло и анализ чувствительности; добавлены проигрываемый граф и итоговая таблица методов.

**Размещение блоков и синхронное масштабирование в разделе «Расчет доверия».** Граф топологии размещён слева от сводной таблицы результатов и занимает меньшую долю ширины. Разделы «Динамика решений и оценок» и «Доверие (репутация) агентов» имеют равную ширину. Временной диапазон обоих графиков синхронизируется: выделите мышью интересующий отрезок на любом графике либо задайте границы в полях «С шага» и «По шаг». Кнопка «Показать весь интервал» возвращает исходный диапазон; при расчёте новой трассы масштаб сбрасывается. Масштабы Y у графиков независимы.

**Принцип интерпретации анимации.** Вычисления по Монте-Карло и демонстрационная покадровая трасса — разные представления. Трасса воспроизводится при установленном зерне и параметрах, но сама по себе не является графиком среднего по всем опытам. Для графо-вероятностного и каскадного экспериментов она соответствует первому испытанию явно названного сценария; для неопределённости и нарушения коллективного решения служит самостоятельной иллюстративной реализацией. Для сети Петри воспроизводится найденная трасса-контрпример либо ожидание при его отсутствии. В исходном Python-ядре журнал конкретных рёбер доставки не сохраняется, поэтому граф расчёта доверия **схематический**, а не точная запись сетевого обмена. Классы топологии при построении схемы отображаются приблизительно, если исходных данных о конкретных рёбрах недостаточно.

### Экспериментальная методика

1. Из выпадающего списка выбирается один из шести экспериментов. У исходного расчёта доверия сохранены режимы «Один прогон», «Монте-Карло», «Чувствительность», «Данные».
2. Задаются численные параметры, включая зерно генератора псевдослучайных чисел и число независимых прогонов.
3. Проверяется допустимость параметров: физически интерпретируемые вероятности лежат в интервале [0, 1], число прогонов и агентов ограничено.
4. Для случайных моделей задаются независимые реализации при последовательной и воспроизводимой инициализации генератора.
5. В ходе моделирования накапливаются индивидуальные исходы, формируется таблица оценок и график сравнения.
6. Результат сохраняется в CSV с UTF-8 BOM и разделителем «;», а также в JSON вместе с настройками и идентификатором постановки.

Используемый xorshift32 с преобразованием Бокса — Мюллера служит только для **имитационного моделирования**, а не для криптографических задач.

#### Оценка статистических характеристик

Для индикатора события A в R независимых прогонах оценивается относительная частота:

\[
\widehat{P}(A)=\frac{1}{R}\sum_{r=1}^R \mathbf{1}\{A_r\}.
\]

Для вещественного ущерба L:

\[
\overline L = \frac{1}{R}\sum_{r=1}^{R} L_r,\qquad
\mathrm{VaR}_{0.95}=Q_{0.95}(L),\qquad
\mathrm{CVaR}_{0.95}=\mathbb E[L\mid L\ge \mathrm{VaR}_{0.95}].
\]

Средняя точность по **всем опытам** не равна точности **среди принятых решений**, если система имеет возможность отказаться от автоматического решения. Эти показатели в первой вкладке представлены отдельно.

#### Принципиальные ограничения

- Графы и коэффициенты интенсивности атак являются условными и не калиброваны по реальным журналам.
- Метод доверительного взвешивания использует условную независимую оценку качества источника. Практическая реализация потребует отдельного механизма верификации.
- Генератор сетей ориентированный и не воспроизводит все свойства реальных сетей агентов.
- Модель Петри реализована как конечный подкласс временной раскрашенной сети с одним типом цвета (идентификатор агента) и единичной задержкой переходов. Вывод «недостижимо» справедлив только при **полном** обходе пространства в пределах установленного горизонта. При превышении лимита вывод изменяется на «не установлено».
- CVaR рассчитывается эмпирически на верхнем хвосте. При небольшом числе прогонов оценка нестабильна.
- Демонстрационные формулы допускают развитие для исследования, но **не должны выдаваться за точные формулы ранее подготовленных статей до сверки их полного текста**.
- Текущая программная проверка состоит из модульных тестов, сборки React и сохранения функциональности исходного Python-ядра. Для публикационной экспериментальной базы дополнительно нужны эталонные данные, доверительные интервалы, проверка чувствительности, оценка вычислительных затрат и независимая научная валидация.

## Хранение результатов браузерной версии и выпуск исходного кода

Все вычисления шести экспериментов выполняются на стороне клиента. Для раздела «Расчет доверия» кэш завершённых серий и контрольные точки сохраняются в локальном IndexedDB под ключом, содержащим параметры эксперимента и режим расчёта. Данные привязаны к браузерному профилю и домену сайта; при очистке данных сайта они удаляются. Никакие результаты автоматически не отправляются в GitHub или Cloudflare.

Серия Монте-Карло и анализ чувствительности выполняются независимыми задачами в пуле Web Workers. Система сохраняет результаты завершённых задач; при остановке потоки завершаются, а повторный запуск с теми же настройками продолжает расчёт с ранее сохранённых задач. Расчёт одной траектории повторяется полностью, если пользователь остановил его до завершения. Допускается экспорт JSON, CSV и SVG через штатные средства интерфейса.

`gui/node_modules/` восстанавливается `npm ci`, `gui/dist/` генерируется `npm run build`. Скриншоты проверки, журналы и временные файлы в Git не включаются. Исходники Python, сохранённые в корне для научной проверки, не используются на опубликованном сайте.

## Публикация в Cloudflare Workers по адресу workers.dev

Тестовый сайт может иметь адрес `https://imas-lab-test.kadet-ilia.workers.dev/`. Окончание **`workers.dev`** обозначает сервис Cloudflare Workers, а не Cloudflare Pages (`pages.dev`). Для браузерного IMAS_LaB_test это допустимый бесплатный вариант, но опубликован должен быть **Vite-каталог `dist`**, а не исходный `index.html` и не Python/Node.js сервер.

Конфигурация `gui/wrangler.toml` задаёт Worker типа **assets-only**: `[assets] directory = "./dist"`, `not_found_handling = "single-page-application"`. Никакой серверный `main` не используется. Обслуживание React, JavaScript-воркеров и CSS выполняет встроенная система статических ресурсов Cloudflare Workers.

Для Git-интеграции Cloudflare Workers Builds в **Settings → Builds** установите:

| Поле Cloudflare Workers | Значение |
|---|---|
| Git repository | `kadet-ilia/IMAS-lab` |
| Production branch | `IMAS_LaB_test` |
| Root directory | `gui` |
| Build command | `npm run build` |
| Deploy command | `npx --yes wrangler@4 deploy` |

Предварительно Cloudflare должен установить npm-зависимости из `gui/package.json`. При стандартном Workers Builds используется npm по обнаруженному манифесту. Если в журнале вместо этого появляется `pip install -r requirements.txt`, неправильно указан корневой каталог сборки.

В отличие от **Pages**, **Workers** имеет *отдельную команду публикации* (`Deploy command`); одной команды `npm run build` недостаточно для обновления активной версии Worker.

Можно повторить публикацию вручную с рабочего ПК при авторизованном Wrangler (однократный вход через браузер):

```bash
cd gui
npm ci
npm run build
npx --yes wrangler@4 login
npx --yes wrangler@4 deploy
```

При успешной публикации проверьте `/index.html` и подключаемые файлы `/assets/...`: JavaScript и CSS должны иметь успешные HTTP-ответы, а не пустое тело, HTML-страницу вместо JS или JSON с ошибкой.

**Диагностика ошибки `Failed to execute 'json' on 'Response': Unexpected end of JSON input`.** Код интерфейса `gui/src` не использует вызовы `Response.json()` или внешние API для расчётов. Поэтому сначала определите, где возникает ошибка: на самом `workers.dev` или в панели Cloudflare. Откройте инструменты разработчика браузера → Network → обновите страницу → найдите запрос, который ожидает JSON, и проверьте его URL, статус, тело ответа и инициатор вызова. Ошибка сама по себе не доказывает неисправность математического ядра. Для корректности публикации необходимо использовать данную конфигурацию статических ресурсов и убедиться в успехе шага Deploy, а не только Build.

Сведения Cloudflare: [Static Assets](https://developers.cloudflare.com/workers/static-assets/), [SPA routing](https://developers.cloudflare.com/workers/static-assets/routing/single-page-application/), [Workers Builds](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/).
